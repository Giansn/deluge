# Rebuilding v16 from the patches, 27.09.2026

Cloud session on `geraet-ergebnisse` (now `device-results`), a task of the development session (state `claude/wizardly-brahmagupta-nnrk07` @ `1238201`).

## Result

- **Bit-identical:** `patches/0001–0055` on `release_1_2_1` give exactly v16 (SHA-256 `7eed1a77a9250918307531b802b9ceb5d95267f48c5e3d67a536848871897f9f`), as soon as the commit hash `c610417f` is in the build.
- **Not with `git am` alone:** `git am` creates new commits with another hash. The hash is in the binary, so the SHA-256 differs. Code and sound are the same anyway (emulator below).
- **Emulator:** Both WAV hashes match, `measured.wav` `87a7df292189e341…` and `digital/measured.wav` `4473b3155dcfa0e8…`.

## Steps

1. Cloned `DelugeFirmware`, `release_1_2_1` = `c23bc2fe`. `git am` 0001–0055: all 55 without a conflict. Tree of the result `380eba66`.
2. Toolchain v16 (dbt, arm-none-eabi-gcc 13.2.1). `./dbt configure -DRELEASE_TYPE:STRING=mastertune-v16`, `./dbt build release`: 1 min 39 s. One linker warning (RWX segment), no other.
3. Two adjustments to the container. Both leave the source tree untouched; it stays clean (otherwise `-dirty` would be in the name):
   - The proxy blocks GitHub archives (403), so `configure` fails on `argon`. I therefore set `-DFETCHCONTENT_SOURCE_DIR_ARGON=` to a clone of `stellar-aria/argon`, tag `v0.1.0` = `caa7cd80`. That is the same commit as in the commented-out `GIT_TAG` in `lib/CMakeLists.txt`. This way CMake doesn't check the tarball's MD5, but the content is fixed by the commit.
   - dbt's Python needs the proxy certificate for pip (`PIP_CERT`).

## Why the hash changes the whole file

- CMake writes `git rev-parse --short HEAD` into the version string `1.2.1-mastertune-v16-<hash>` and into `kCommitShort`.
- `handle_cpu_fault()` shows the first 4 hex characters of the hash on the pads after a crash. LTO folds these characters in as constants. With `0fc5` instead of `c610` the function gets 30 bytes longer, and everything from `routineForSD` on lies 32 bytes further back. That's why 797,959 bytes differ, at the same file size.
- Nothing else is embedded, neither the build path nor the date (checked with `strings`).

## The original hashes can't be rebuilt

- The `From` lines of the patches are the original commits: 0001 = `49e71650`, 0055 = `c610417f`. The older releases carry the same names (v3 `09dcce01` and so on).
- Committer = author and time = author time hits none of the 55 hashes, neither signed nor unsigned. For 0001 I also searched committer times from −1 h to +3 days, with two identities and two time zones: no hit.
- The commits were probably signed. This container signs every commit by SSH (`commit.gpgsign=true`); then the hash depends on the signature and the key. That can't be rebuilt.

## Recipe for rebuilding

```sh
git clone https://github.com/SynthstromAudible/DelugeFirmware && cd DelugeFirmware
git checkout release_1_2_1 && git config core.abbrev 8
ls /path/to/patches/00*.patch | head -55 | GIT_COMMITTER_NAME=Claude GIT_COMMITTER_EMAIL=noreply@anthropic.com \
  xargs git -c commit.gpgsign=false am --committer-date-is-author-date      # HEAD 0fc5d96e, the same for everyone
./dbt configure -DRELEASE_TYPE:STRING=mastertune-v16                         # here also -DFETCHCONTENT_SOURCE_DIR_ARGON=…
# in build/src/deluge/version/version.cmake replace the execute_process with "rev-parse --short HEAD"
# by  set(GIT_COMMIT_SHORT "c610417f")
./dbt build release                                                          # 7eed1a77… = v16
```

## Suggestion

If future releases are to be rebuildable from the patches without intervention, there are two ways:

- **A deterministic chain:** Before the release build, rebuild the chain as above, i.e. unsigned and with committer time = author time, and build from it. Then the command gives everyone the same hash and the same file.
- **Fix the hash:** a CMake variable that overrides `GIT_COMMIT_SHORT`, and the value in the README.
