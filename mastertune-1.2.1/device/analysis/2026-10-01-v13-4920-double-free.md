# #4920: can ParamManager::stealParamCollectionsFrom() free shared collections? 01.10.2026

This compares upstream beta `62a516c2` with mastertune (1.2.1 plus patches). Upstream's fix `47b1d92b` (#4920) frees the destination's main collections before it takes the source's. The question: does any caller pass in a destination whose collections another ParamManager still holds?

## Verdict: all 11 callers are safe

- **The loop frees nothing today.** The new loop (`src/deluge/modulation/params/param_manager.cpp:128-136`) frees only the destination's `summaries[0 .. expressionParamSetOffset)`. At every call site that offset is 0, because the destination is fresh, emptied just before, or guarded.
- **The fix's one effective change** is `song.cpp:3942` (`backedUp->~BackedUpParamManager()`). It frees the expression set that `steal(..., false)` leaves in the removed backup, and nothing else holds that set.

No other sharing paths turned up:
- `InstrumentClip::clone()` deep-copies the managers (`instrument_clip.cpp:169`).
- Kit rows are copied, then cloned in place.
- Backups are moved, never copied.

**Latent trap, in both trees:**
- A failed `cloneParamCollectionsFrom()` resets summaries 0 and 1 (`param_manager.cpp:218`) but keeps `expressionParamSetOffset`.
- A kit row whose `beenCloned()` failed for lack of RAM (`note_row.cpp:105`) therefore keeps offset 3 while holding the source row's collections.
- A future caller that steals into it without forgetting first would free shared memory. None of the 11 callers does that today.

## mastertune

- **Same callers:** the same 11 callers with the same guards:
  - `song.cpp:3723/3770/3810/3863/3879/3900`
  - `instrument_clip.cpp:1584/2170/2178`
  - `clip.cpp:922`
  - `note_row.cpp:3496`

  They differ from the beta only in NULL/nullptr and the #4920 edits. Our patches add no caller.
- **1.2.1's function** (`param_manager.cpp:113-162`) has no free loop. With empty destinations it leaks nothing.
- **The real leak in 1.2.1** is at `song.cpp:3863-3867`. There, `deleteAtIndex()` runs no destructor, so a backup's expression set is lost.
- **Porting `47b1d92b` as is** adds no reachable double free, since its loop is dead in every caller. It fixes that leak.

An agent read the callers. The core claims were then checked in the code: the loop's bound, `song.cpp:3942` in the beta, and `song.cpp:3863-3867` in 1.2.1.
